# 迭代记录

## 2026-08-31 · MVP v0.7 实施进度

### 真实双边案例与定向澄清

- 默认真实市场只比较数据库中的真实租客与真实房源；演示语料与真实双边案例完全分离。
- 每一对真实任务只有一个权威案例，双方候选投影在同一事务写入；输入版本变化会重算并产生新条款版本。
- 无硬冲突但信息不足时，规则每轮最多选择三个高价值问题，按资格安全、硬条件、价格租期费用和沟通成本排序。
- 问题只发给能够回答的一方；本人可见具体问题，对方仅可见待补充数量和粗粒度类别。
- 回答由固定 schema 校验，并原子写入 `counterparty_answer` 字段版本、任务输入版本、案例事件和 outbox；随后自动重算为继续澄清、条款就绪或冲突失效。
- Qwen 只能润色规则已经选定的问题，不能修改字段、答案类型或枚举选项；不可用或输出越界时回退到规则模板。
- 使用 `Qwen/Qwen3.5-35B-A3B` 完成单次真实契约冒烟：严格字段校验通过，消耗 254 tokens，API Key 未进入仓库或报告。
- 有效匿名会话在页面刷新时复用原账号，不再因为重复调用会话入口而丢失任务与候选。

### 界面

- 租客房源详情与出租方租客详情都接入真实案例进度。
- 单选、数值、日期、日期范围和短文本分别使用对应控件；提交期间明确显示“正在写入新版本并重新匹配”。
- 未完成阻断澄清时，页面不会允许继续执行双方确认。
- Playwright 已验收 390×844 与 320×568：无横向溢出；案例回答前后状态正确；控制台在服务器稳定运行期间为 0 错误、0 警告。

## 2026-08-23 · MVP v0.1

### 已验证的产品判断

- 入口应是“创建委托”，而不是“浏览帖子”。
- AI 补问必须把硬条件与加分偏好分开，否则用户不知道为什么少了候选。
- 候选卡必须同时展示匹配理由、明显缺点和事实来源。
- 双方 AI 对话应表现为可审计事件，不展示隐藏思维或对方私密底价。
- 强处罚与防恶意举报可以兼容：举报后立即隔离，客观证据确认后再执行实名级永久封禁。

### 本轮自动发现并修复

1. **过期房源状态枚举不一致**
   - 底层使用 `exclude`，汇总层只识别 `excluded`。
   - 影响：已排除数量少算，测试台误判。
   - 修复：统一为 `excluded`，加入自动回归。

2. **新页面继承旧页面滚动位置**
   - 从较长的委托确认页提交后，结果页可能直接落在候选卡中部。
   - 影响：用户错过 AI 扫描和风控摘要。
   - 修复：以导航视图键区分页面；跨页面切换归零，同页交互保留滚动。

3. **补问答案只改文案、不改规则的风险**
   - 初版模拟数据固定使用默认委托。
   - 影响：“必须独卫”“不接受合租”等选择可能成为假交互。
   - 修复：提交时从界面答案构造真实委托，硬条件进入引擎判定。

4. **浏览器缺少 favicon 产生 404**
   - 影响：控制台不干净，可能掩盖真实资源错误。
   - 修复：复用本地应用图标，并重新验证控制台为 0 错误、0 警告。

5. **桌面预览可能产生外层页面滚动**
   - 影响：设备框顶部在自动点击后可能被浏览器滚出视口。
   - 修复：锁定外层页面滚动，仅允许应用主内容区滚动。

### 下一轮优先验证

1. 用户是否理解“私密授权”和“非约束性意向”的区别。
2. 三套候选是否足够，还是需要“再找一轮”而不是增加一次交付数量。
3. 中介识别失败时，用户最愿意提供哪类证据。
4. 出租方是否愿意先提交角色与权利材料，再看到潜在租户。
5. 协商事件应默认展开多少，既能建立信任又不会造成信息负担。
